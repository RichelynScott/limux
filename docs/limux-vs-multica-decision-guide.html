Decision Options

These are the practical choices from the analysis.

Recommended

Keep Limux + hcom primary

Context: Your current workflow depends on live panes and direct operator intervention. Why: This preserves that while testing Multica's ledger value. Risk: Multica's value remains unproven until a pilot.

Possible

Use Multica as async layer

Context: Multica's strongest surface is issues, comments, runs, and squads. Why: It avoids replacing Limux. Risk: Adds ops burden.

Conservative

Stay Limux-only for now

Context: You can copy Multica ideas without adopting the stack. Why: Lowest external-tool risk. Risk: Requires Limux/hcom feature work.

Risks That Matter

These are the blockers to resolve before using Multica for serious work.

Multica blockers

Do not ignore these

  • Codex subagents are disabled by default because child output can be dropped.
  • Codex session resumption is documented as unusable.
  • No native quorum, vote, approval gate, or consensus primitive was found.
  • Installer, Docker, desktop, daemon, and third-party skill surfaces need review.
  • Local-directory execution can mutate real repos in place.
  • The license is not plain Apache-2.0 and needs review for external service use.
Limux fixes

Make Limux safer

  • Shipped: `agent-team` no longer writes `AGENTS.md` by default.
  • Shipped: `--protocol-path` allows explicit sidecar location.
  • Next: add `Instruction Sources` to `LIMUX_AGENTS.md` without copying repo instruction files.
  • Next: add generated-marker and no-overwrite behavior for existing unmarked sidecars.
  • Add a project/team roster for 4+ project coordination.
  • Add a durable review and consensus ledger.
  • Improve transcript capture beyond visible viewport reads.
